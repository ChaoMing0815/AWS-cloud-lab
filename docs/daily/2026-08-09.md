## 建議 API 邊界

### 玩家星火決策

```http
PUT /api/v1/rooms/{room_id}/rounds/{round_number}/spark
```

Request：

```json
{
  "decision": "USE | DECLINE",
  "room_version": 12
}
```

Owner 必須由 player session 判定，不接受前端傳入 `player_id`。

### 房主結算

```http
POST /api/v1/rooms/{room_id}/rounds/{round_number}:resolve
```

Request：

```json
{
  "skip_pending_spark": false,
  "room_version": 15
}
```

`skip_pending_spark=false` 時，尚有玩家未決定必須回傳 conflict；房主明確設為 `true` 才能將等待者視為 `DECLINE`。結算必須具備 host session、host CSRF、version 與 scoped idempotency。

## 測試案例最低集合

### 規則測試

- 原始 6 使用星火後為 7：`FAILURE → PARTIAL_SUCCESS`。
- 原始 9 使用星火後為 10：`PARTIAL_SUCCESS → SUCCESS`。
- 原始 5 使用星火後仍為 6：維持 `FAILURE`，結算後補回 1 星火。
- `DECLINE` 不改變骰點、結果或星火。
- 星火不得低於 0、高於 3。

### 安全與一致性測試

- 匿名或其他玩家不能替本人決策。
- 玩家 CSRF 錯誤回傳 403。
- 非房主不能結算。
- 舊 room version 回傳 409。
- 同一 idempotency key replay 不重複扣星火、不重複加點、不重複建立故事或前進回合。
- `AWAITING_SPARK` 以外狀態拒絕星火決策與結算。
